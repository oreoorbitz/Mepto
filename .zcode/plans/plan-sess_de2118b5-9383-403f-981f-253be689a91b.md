## Mepto vs jQuery Compare Feature

### Goal

Run each test case against both Mepto and jQuery (as `$`), diff the results, and report divergences. Directly serves the library's "jQuery-compatible" goal by surfacing behavioral mismatches.

### How `$` swapping works

User code's bare `$` resolves to `window.$` at `eval` time (the async IIFE in `execute()` has no closure capture). So for the jQuery run: inject jQuery via `addScriptTag({ path })`, then reassign `window.$ = window.jQuery`. For the Mepto run: change nothing (`blank.html` already sets `window.$` from source).

### jQuery source

Add `jquery` as a **devDependency** of the harness (`tools/llm-test-harness/package.json`). Inject from `node_modules/jquery/dist/jquery.js` via `page.addScriptTag({ path })` — filesystem read bypasses the request-interception layer that blocks non-localhost URLs. No CDN, no security hole, reproducible.

### Implementation (4 files)

**1. `tools/llm-test-harness/package.json`** — add `"jquery": "^3.7.1"` to `devDependencies`, run `npm install`.

**2. `src/runner.ts`** — add the diff engine:

- New types: `ComparisonCaseResult` (a case's outcome on both libs + a `match: boolean` flag), `CompareResult` (array of comparisons + summary).
- New method `TestRunner.runCompare(cases, defaults)`: for each case, create a fresh page, load HTML (Mepto already on `$`), execute → record Mepto result. Then on the **same page** inject jQuery and reassign `window.$ = window.jQuery`, re-inject the fixture HTML fresh (so both libs start from identical DOM), execute the same code → record jQuery result. Diff the two `result`/`error`/`assertions` fields.
- Handle jQuery's UMD auto-binding: before `addScriptTag`, clear `window.$`/`window.jQuery`/`window.mepto` so jQuery's factory doesn't fight Mepto's globals; after injection, explicitly set `window.$ = window.jQuery`.
- Compare semantics: a case "matches" if both libs produced the same `result` (deep-equal) and the same error/no-error. Assertion tallies are reported side-by-side but don't gate `match` (assertions are about the _test's_ expectations, not library behavior).

**3. `src/index.ts`** — add `LLMTestHarness.runCompare(cases, options)` mirroring `runBatch`'s server/browser lifecycle (detect server once, init browser once, run all comparisons, close once). Export the new types.

**4. `bin/mepto-test.js`** — add `--compare` flag. When combined with `--batch <file>`, route to `harness.runCompare()` instead of `runBatch()`. Output: per-case table showing `Mepto: <value>` vs `jQuery: <value>` with a `MATCH`/`DIFF` marker, plus a summary count. Exit 0 only if all cases match.

### Reusing the existing fixture-injection pattern

Both runs use the same `loadHTML(html, port)` → fixture into `#test-container` pattern. For the jQuery run, after swapping `$`, re-run the fixture injection so jQuery operates on clean DOM identical to what Mepto saw.

### Scope note / honest limitation

This compares **return values** of the same code under each `$`. It won't catch differences in side-effects on the DOM unless the test code returns/inspects them (e.g. `return el.outerHTML`). That's a reasonable v1 — agents can write cases that return the observable state they care about. Deeper DOM-state diffing is a possible later enhancement.
